# Веб-конфигуратор сборки ПК с рекомендательной системой

[![CI](https://github.com/r0st-ma1n/WebConfigPC/actions/workflows/ci.yml/badge.svg)](https://github.com/r0st-ma1n/WebConfigPC/actions/workflows/ci.yml)

Учебный проект. Пользователь описывает задачи и бюджет, а система:

- подбирает 2–3 совместимые сборки: «Дешевле», «Оптимальная», «С запасом»;
- объясняет, почему выбраны именно эти детали;
- предлагает замены: что даст доплата за конкретную деталь и где можно сэкономить без заметной потери.

Есть ручной режим: пользователь собирает ПК по шагам и видит только совместимые детали.
ИИ (LLM) разбирает запрос в свободной форме и пересказывает объяснение простым языком.
Сами сборки подбирает алгоритм, а не модель. Без ключа API приложение работает полностью.

## Быстрый запуск (Docker)

Нужен только Docker с Docker Compose.

```bash
cp .env.example .env
docker compose up -d --build
```

Приложение откроется на http://localhost:8090 (порт меняется переменной `APP_PORT`).
При старте бэкенд применяет миграции и заполняет пустую базу тестовыми данными.
nginx раздаёт собранный фронтенд и проксирует `/api` на бэкенд.

## Запуск для разработки

Нужны: Python 3.14 и [uv](https://docs.astral.sh/uv/), Docker с Docker Compose, Node.js 20+.

```bash
# 1. Настройки окружения
cp .env.example .env

# 2. Только база данных (PostgreSQL в Docker, порт на хосте 5433)
docker compose up -d db

# 3. Зависимости бэкенда
uv sync

# 4. Миграции и тестовые данные
cd backend
uv run alembic upgrade head
uv run python -m app.seed

# 5. Бэкенд: http://localhost:8000, документация API: http://localhost:8000/docs
uv run uvicorn app.main:app --reload

# 6. Фронтенд (в отдельном терминале, из корня проекта): http://localhost:5173
cd frontend
npm install
npm run dev
```

Vite проксирует запросы `/api/*` на бэкенд, поэтому отдельно настраивать адрес API не нужно.

### Подключение ИИ (необязательно)

В `.env` укажите провайдера и ключ:

```ini
# Anthropic (модель по умолчанию — claude-opus-5-5)
LLM_PROVIDER=anthropic
LLM_API_KEY=sk-ant-...

# или любой OpenAI-совместимый API
LLM_PROVIDER=openai
LLM_API_KEY=...
LLM_MODEL=имя-модели
LLM_BASE_URL=https://адрес-api/v1   # для OpenAI можно не указывать
```

После изменения `.env` перезапустите бэкенд. Статус виден в правом верхнем углу интерфейса.

Если бэкенд запущен в Docker, а модель — на этом же компьютере (LM Studio, Ollama),
в `LLM_BASE_URL` вместо `localhost` укажите `host.docker.internal`, например
`http://host.docker.internal:1234/v1`.

## Тесты и проверки

```bash
uv run pytest                     # тесты
uv run ruff check backend         # линтер
cd backend && uv run mypy         # проверка типов
cd frontend && npm run lint && npm test && npm run build
```

Те же проверки запускает GitHub Actions на каждый push и pull request
(`.github/workflows/ci.yml`). В CI тесты идут с настоящим PostgreSQL, а в конце
собирается и запускается весь стек в Docker и проверяется подбор через nginx.

Тесты не требуют запущенной базы: модули совместимости и подбора работают с объектами
в памяти, а API-тесты подменяют загрузку каталога данными из JSON. Единственный тест,
который обращается к PostgreSQL, пропускается, если база не запущена. ИИ тестируется
с фейковым провайдером, реальных запросов к модели нет.

| Файл | Что проверяет |
|---|---|
| `test_catalog.py` | полнота и согласованность тестовых данных, загрузка из БД |
| `test_compatibility.py` | каждое правило совместимости: случай с нарушением и без |
| `test_recommender.py` | распределение бюджета, модель оценки, свойства подбора, предпочтения, замены, объяснения |
| `test_api.py` | эндпоинты, валидация, ошибки, применение замены |
| `test_ai.py` | разбор запроса правилами и через LLM, запасные варианты при ошибках LLM |
| `test_eval_explanations.py` | проверки скрипта оценки объяснений |

### Оценка точности объяснений

Модульные тесты не проверяют, что пишет настоящая модель. Для этого есть скрипт: он
генерирует объяснения для нескольких типовых сборок через провайдер из `.env` и ищет
типичные ошибки — выдуманные предупреждения и экономию, «дороже бюджета» для сборки
в бюджете, числа, которых нет в данных, служебные слова из JSON, не тот тип памяти.

```bash
uv run python backend/scripts/eval_explanations.py --runs 3 --out eval.json
uv run python backend/scripts/eval_explanations.py --rescore eval.json   # перепроверить без генерации
```

База и бэкенд не нужны. Скрипт стоит запускать после правок промпта или смены модели.
Проверки ловят не всё (например, неверную оценку доплаты), поэтому сохранённые тексты
полезно просмотреть.

## Архитектура

```
┌──────────────────────────── Фронтенд (React) ────────────────────────────┐
│  Подбор: описание словами / форма → варианты → объяснение → замены       │
│  Ручная сборка: шаги → только совместимые детали → итог и предупреждения │
└───────────────────────────────────┬──────────────────────────────────────┘
                                    │ REST /api
┌───────────────────────────────────▼──────────────────────────────────────┐
│ FastAPI (app/api)                                                        │
│   components ── compatibility ── recommend ── ai                         │
├──────────────────────────────────────────────────────────────────────────┤
│ Предметная логика (не зависит от БД и веба)                              │
│   domain.Build        — сборка как набор деталей                         │
│   compatibility/      — правила совместимости                            │
│   recommender/        — бюджет, оценка, поиск, замены, объяснения        │
│   ai/                 — провайдеры LLM, разбор запроса, объяснения       │
│   prices/             — заглушка для будущего парсера цен                │
├──────────────────────────────────────────────────────────────────────────┤
│ SQLAlchemy-модели (models.py) ── Alembic-миграции ── PostgreSQL          │
└──────────────────────────────────────────────────────────────────────────┘
```

Главное решение: модули совместимости и подбора работают с обычными объектами
в памяти и ничего не знают о базе и HTTP. Каталог небольшой (138 позиций), поэтому
на каждый запрос он загружается из БД целиком одним запросом с JOIN и передаётся
в алгоритм. Так логику легко тестировать и объяснять.

## Схема БД

Используется наследование таблиц (joined table inheritance). Общие поля всех
комплектующих хранятся в `components`, характеристики категории — в отдельной
таблице, связанной с `components` по `id` (1:1). SQLAlchemy по полю `category`
понимает, объект какого класса создать.

```
components (id PK, category, brand, name, price_rub, perf_score, power_w, price_updated_at)
   ├── cpus          (id PK/FK → components.id, ...)
   ├── gpus          (id PK/FK, ...)
   ├── motherboards  (id PK/FK, ...)
   ├── rams          (id PK/FK, ...)
   ├── storages      (id PK/FK, ...)
   ├── psus          (id PK/FK, ...)
   ├── cases         (id PK/FK, ...)
   └── coolers       (id PK/FK, ...)
```

| Таблица | Поля |
|---|---|
| `components` | id, category, brand, name, price_rub, perf_score (0–100), power_w, price_updated_at |
| `cpus` | socket, cores, threads, base_ghz, boost_ghz, memory_types[], has_igpu, includes_cooler, multicore_score |
| `gpus` | chip, vram_gb, length_mm, recommended_psu_w |
| `motherboards` | socket, chipset, form_factor, memory_type, memory_slots, max_memory_gb, m2_slots |
| `rams` | memory_type, capacity_gb, modules, speed_mhz |
| `storages` | kind (NVMe / SATA_SSD / HDD), interface (M.2 / SATA), capacity_gb |
| `psus` | wattage, efficiency |
| `cases` | supported_form_factors[], max_gpu_length_mm, max_cooler_height_mm, max_radiator_mm |
| `coolers` | kind (air / aio), height_mm, radiator_mm, sockets[], max_tdp_w |

`perf_score` — оценка производительности внутри категории (0–100). У процессоров это
игровая производительность (100 = Ryzen 7 9800X3D), многопоточная (рендер, видео)
хранится отдельно в `cpus.multicore_score`. У видеокарт 100 = RTX 5090. Оценки
приблизительно отражают соотношения из общедоступных тестов.

Тестовые данные: `backend/app/seed/components.json`. В нём 138 позиций (15–23 на
категорию), платформы AMD AM4/AM5 и Intel LGA1700/LGA1851, цены от бюджетного
до топового сегмента. Цены примерные и служат только для демонстрации.

## Модуль совместимости

`backend/app/compatibility/`. Сборка проверяется набором независимых правил.
Каждое правило — функция `(сборка) -> список нарушений`. Нарушение содержит:
- уровень: `error` — собрать нельзя, `warning` — собрать можно, но есть риск;
- машинный код;
- понятный текст;
- id затронутых деталей.

Правило проверяет только уже выбранные детали, поэтому модуль работает и с неполной сборкой.

| Правило | Уровень | Что проверяет |
|---|---|---|
| `cpu_motherboard_socket` | error | сокет процессора и платы |
| `cooler_socket` | error | кулер поддерживает сокет |
| `cooler_tdp` | warning | кулер справляется с тепловыделением CPU |
| `board_vrm` | warning | мощный процессор (от 150 Вт) на плате начального уровня (A520, A620, H610) |
| `ram_type` | error | тип памяти: RAM ↔ плата ↔ процессор |
| `ram_slots_and_capacity` | error | число модулей ≤ слотов, объём ≤ максимума платы |
| `m2_slots` | error | хватает слотов M.2 |
| `board_form_factor` | error | форм-фактор платы поддерживается корпусом |
| `gpu_length` | error | видеокарта помещается в корпус |
| `cooler_fits_case` | error | высота кулера / размер радиатора СЖО |
| `psu_power` | error / warning | мощность БП ≥ потребления; запас ≥ 30% и не ниже рекомендации производителя GPU |
| `cpu_gpu_balance` | warning | процессор не ограничивает видеокарту и не избыточен для неё (с учётом разрешения) |

Для законченной сборки (`complete=True`) дополнительно проверяется, что выбраны
все обязательные детали, есть вывод изображения (видеокарта или встроенная графика)
и охлаждение (отдельный кулер или боксовый).

- **Потребление сборки** — сумма `power_w` всех деталей.
- **Рекомендуемый БП** — потребление × 1,3, округлённое вверх до 50 Вт, но не ниже
  рекомендации производителя видеокарты.
- **Баланс CPU/GPU** (`app/balance.py`). Шкалы оценок CPU и GPU разные, поэтому процессор
  считается достаточным, если `cpu_score ≥ gpu_score × K` (допуск 3%). K зависит от
  разрешения: 1,2 для 1080p, 1,0 для 1440p, 0,7 для 4K. Чем выше разрешение, тем больше
  нагрузка ложится на видеокарту. Процессор избыточен, если `cpu_score > gpu_score × 2,7`.
- **Ручной режим** использует `candidate_errors(сборка, деталь)`: деталь показывается,
  если её установка не порождает ошибок, в которых участвует она сама. Несовместимые детали
  можно показать вместе с причиной.

## Алгоритм рекомендаций

`backend/app/recommender/`. Вход — `RecommendRequest`:
- бюджет;
- сценарий (`gaming`, `workstation`, `office`);
- разрешение (для игр);
- необязательно: платформа (AMD/Intel), конкретный процессор или видеокарта.

### 1. Распределение бюджета (`budget.py`)

Для каждого сценария задана таблица долей:

| | CPU | GPU | Плата | RAM | SSD | БП | Корпус | Охлаждение |
|---|---|---|---|---|---|---|---|---|
| Игры | 20% | 40% | 10% | 8% | 7% | 7% | 5% | 3% |
| Видео и 3D | 30% | 28% | 10% | 12% | 8% | 6% | 4% | 2% |
| Офис и учёба | 35% | 0% | 15% | 12% | 15% | 10% | 10% | 3% |

В играх доля видеокарты зависит от разрешения: −4% в 1080p, +6% в 4K. Эти проценты
забираются у процессора (60%) и платы (40%).

Доли — ориентир для второстепенных деталей: в каждой категории берётся лучшая деталь,
которая укладывается в свою долю. Процессор и видеокарта перебираются полностью
(шаг 3), поэтому их доли используются для сравнения «план / факт» на диаграмме.

### 2. Оценка сборки (`scoring.py`)

Оценка 0–100 — взвешенная сумма оценок по «ролям»:

```
score = Σ вес(сценарий, роль) × оценка(роль)
```

| Роль | Игры | Видео и 3D | Офис |
|---|---|---|---|
| игровая производительность связки CPU+GPU | 0,80 | — | — |
| процессор | 0,05 (игровая) | 0,34 (многопоточная) | 0,50 (среднее) |
| видеокарта | — | 0,34 | — |
| память | 0,07 | 0,16 | 0,20 |
| накопитель | 0,05 | 0,11 | 0,25 |
| платформа (плата, БП, корпус, охлаждение) | 0,03 | 0,05 | 0,05 |

Ключевые идеи модели:

- **Число кадров определяет более слабое звено.**
  `gaming = min(gpu_score, cpu_score / K(разрешение))`. Деньги, вложенные в видеокарту
  сверх возможностей процессора (или наоборот), оценку не повышают. Поэтому алгоритм
  сам выбирает сбалансированные пары.
- **Убывающая отдача.** Объём памяти и накопителя сверх полезного для сценария не повышает
  оценку. Для памяти это 32 ГБ в играх, 128 ГБ в работе, 16 ГБ в офисе; для накопителя —
  2, 4 и 1 ТБ. Все NVMe считаются одинаково быстрыми: разница между бюджетным и топовым
  в играх и офисе почти незаметна.
- **Двухканальная память.** Один модуль памяти штрафуется, а при встроенной графике сильнее:
  она использует ОЗУ как видеопамять.
- **Видеокарты для 3D.** В сценарии «Видео и 3D» видеокарты не NVIDIA учитываются
  с коэффициентом 0,8: в Blender и DaVinci Resolve NVIDIA быстрее за счёт CUDA/OptiX.

### 3. Поиск сборок (`builder.py`)

Для каждого варианта задан предел цены: «Дешевле» — 80% бюджета, «Оптимальная» — 100%,
«С запасом» — 115%.

1. **Перебор пар.** Перебираются все пары (процессор, видеокарта) с учётом предпочтений.
   Для офиса видеокарта не ставится, а процессор нужен со встроенной графикой.
   Каталог небольшой (~23 × 19 пар), поэтому полный перебор занимает доли секунды
   и даёт точный результат.
2. **Достройка.** Каждая пара достраивается до полной сборки: плата → память →
   накопитель → кулер → корпус → блок питания. Для каждой детали берутся только
   совместимые варианты, отвечающие требованиям сценария. Из них выбирается деталь
   с наибольшим вкладом в оценку в пределах своей доли бюджета, при равенстве — более
   дешёвая. Если в долю не укладывается ничего, берётся самая дешёвая.
3. **Требования сценария.** Сборки ниже этого уровня не рассматриваются:
   - минимум памяти: в играх 16 ГБ, при бюджете от 90 тыс. — 32 ГБ;
   - системный диск — только SSD;
   - видеопамяти не меньше 8 ГБ;
   - блок питания только с сертификатом 80 PLUS;
   - нет предупреждений о слабом кулере, нехватке запаса БП и слабом питании платы.
4. **Докупка улучшений.** Лучшие 12 сборок «докупаются»: оставшиеся деньги жадно тратятся
   на замену второстепенной детали с лучшим приростом оценки на рубль. Улучшение
   принимается, только если оно даёт не меньше 30% от средней «оценки за рубль» всей
   сборки, иначе деньги не тратятся. Так система не тратит бюджет на то,
   что почти не влияет на результат.
5. **Выбор.** Берётся сборка с наибольшей оценкой, а если несколько сборок отличаются
   меньше чем на 1% — самая дешёвая. У варианта «С запасом» к оценке добавляется бонус
   за возможность апгрейда:
   - +3 за актуальный сокет AM5/LGA1851;
   - +2 за блок питания с запасом 50%;
   - +1 за свободные слоты памяти.
6. **Отсев похожих.** Победители более дешёвых вариантов участвуют в выборе более дорогих,
   поэтому более дорогой вариант никогда не хуже. Вариант показывается, только если он
   хотя бы на 2% лучше предыдущего. Поэтому иногда вариантов два, а не три.

Если даже самая дешёвая подходящая сборка дороже бюджета, пользователь получает
понятное сообщение с минимальной суммой.

### 4. Замены (`alternatives.py`)

Для каждой детали перебираются все детали той же категории. Если замена ломает
совместимость (например, процессор другого сокета), зависимые детали подбираются
заново самые дешёвые (`BuildSearch.repair`), и все вынужденные изменения показываются
пользователю. Для каждой замены считаются разница в цене и изменение оценки в процентах.

- **«Что даст доплата»:** прирост ≥ 2%, доплата ≤ 30% бюджета, лучшие по приросту на рубль.
  Доплата с низкой отдачей помечается «мало пользы за эти деньги».
- **«Где сэкономить»:** экономия ≥ 1000 ₽ при потере не больше 3%.
- Закреплённые пользователем процессор и видеокарта не заменяются.

Любую замену можно применить одним нажатием: сборка пересчитывается через
`POST /api/recommend/evaluate`, и для неё строятся новые замены.

### 5. Объяснение (`explain.py`)

Из сборки собираются «факты»:
- распределение денег;
- что ограничивает FPS;
- запас блока питания;
- платформа;
- предупреждения;
- лучшие замены.

По фактам строится шаблонное объяснение. Если подключён ИИ, те же факты в JSON
передаются модели с инструкцией пересказать их простым языком, ничего не добавляя от себя.

## Слой ИИ

`backend/app/ai/`. Провайдер заменяемый: интерфейс `LLMProvider` (`base.py`) содержит
два метода — `generate_json` и `generate_text`. Реализации:

- `AnthropicProvider` — официальный SDK `anthropic`, структурированный вывод по JSON-схеме.
  Если классификатор безопасности модели ошибочно отклонит запрос, работает серверный
  запасной вариант (`fallbacks`).
- `OpenAICompatibleProvider` — SDK `openai` с настраиваемым `base_url`. Подходит для OpenAI,
  DeepSeek, локальной Ollama и других совместимых сервисов.

Чтобы добавить провайдера, нужно реализовать два метода и добавить его в `factory.py`.

| Задача | С LLM | Без LLM или при ошибке |
|---|---|---|
| Разбор запроса («хочу играть в 1440p до 120 тысяч») | модель извлекает бюджет, сценарий, разрешение, платформу, модели деталей; ответ проверяется Pydantic | разбор по ключевым словам и регулярным выражениям (`rules_parser.py`) |
| Объяснение сборки | модель пересказывает факты простым языком | шаблонное объяснение |

Названия деталей из запроса («RTX 5070») сопоставляются с каталогом, и такая деталь
закрепляется в подборе.

## API

Интерактивная документация: `http://localhost:8000/docs`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/components?category=` | каталог комплектующих |
| POST | `/api/components/options` | варианты для шага ручной сборки с отметкой совместимости и причинами |
| POST | `/api/compatibility/check` | проверка сборки, цена, потребление, рекомендуемый БП |
| POST | `/api/recommend` | подбор сборок |
| POST | `/api/recommend/evaluate` | оценка произвольной сборки (применение замены) |
| GET | `/api/ai/status` | подключён ли ИИ |
| POST | `/api/ai/parse` | свободный текст → параметры подбора |
| POST | `/api/ai/explain` | объяснение сборки (LLM или шаблон) |

## Цены

Цены хранятся в базе. Модуль `app/prices/provider.py` содержит интерфейс
`PriceProvider.fetch_prices(components) -> list[PriceQuote]`, заглушку
`StaticPriceProvider` и функцию `update_prices(session, provider)`, которая
записывает новые цены в базу. Чтобы подключить парсер магазина, достаточно
написать класс с методом `fetch_prices`.
