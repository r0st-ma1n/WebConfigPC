# Веб-конфигуратор сборки ПК с рекомендательной системой

[![CI](https://github.com/r0st-ma1n/WebConfigPC/actions/workflows/ci.yml/badge.svg)](https://github.com/r0st-ma1n/WebConfigPC/actions/workflows/ci.yml)

Веб-приложение для подбора сборки ПК. Пользователь описывает задачи и бюджет, а система:

- подбирает 2–3 совместимые сборки: «Дешевле», «Оптимальная», «С запасом»;
- объясняет, почему выбраны именно эти детали;
- предлагает замены: что даст доплата за конкретную деталь и где можно сэкономить без заметной потери.

Есть ручной режим: пользователь собирает ПК по шагам и видит только совместимые детали.
Сборкой можно поделиться: она сохраняется в базе и открывается по короткой ссылке `/b/<код>`.
ИИ (LLM) разбирает запрос в свободной форме и пересказывает объяснение простым языком.
Сами сборки подбирает алгоритм, а не модель. Без ключа API приложение работает полностью.

## Главное

- **Подбор — алгоритм, а не LLM**: проверка совместимости по 14 правилам, полный перебор
  вариантов, результат воспроизводим и покрыт тестами. Модель только разбирает запрос
  и пересказывает готовый результат, а при её ошибке работают правила и шаблоны
  ([подробнее](#сборки-подбирает-алгоритм-а-не-llm)).
- **Нагрузочный тест на k6 нашёл две реальные проблемы**: у nginx кончались порты (17–34%
  ответов 502) и тяжёлый подбор задерживал лёгкие запросы того же воркера (GIL). После
  keepalive в nginx и кэша результатов в Redis — 88 RPS без ошибок, p95 лёгких запросов
  около 60 мс ([цифры до и после](#нагрузочное-тестирование)).
- **Метрики сразу нашли третью**: под нагрузкой Redis ложно считался недоступным из-за
  таймаута чтения ([мониторинг](#метрики-и-мониторинг)). Prometheus и Grafana с дашбордом
  и алертами из репозитория.
- **Redis без единой точки отказа**: общий для воркеров лимит запросов (Lua, атомарно), кэш
  с отпечатком каталога вместо ручной инвалидации; если Redis падает, предохранитель
  переключает всё на память процесса ([подробнее](#redis--общее-состояние-воркеров-каталог--в-памяти-процесса)).
- **Вход на сессиях в базе, а не на JWT**: выход срабатывает сразу, argon2id, защита от
  перебора паролей ([почему так](#вход--сессии-в-базе-а-не-jwt)).
- **Контракт API под контролем**: типы фронтенда генерируются из OpenAPI, CI падает при
  расхождении ([подробнее](#типы-фронтенда-генерируются-из-openapi)).
- **Качество**: 200+ тестов бэкенда, Vitest и Playwright e2e на фронтенде, ruff и mypy,
  CI собирает и проверяет весь стек в Docker, включая мониторинг.

## Быстрый запуск (Docker)

Нужен только Docker с Docker Compose.

```bash
cp .env.example .env
docker compose up -d --build
```

Приложение откроется на http://localhost:8090 (порт меняется переменной `APP_PORT`).
При старте бэкенд применяет миграции и заполняет пустую базу тестовыми данными.
nginx раздаёт собранный фронтенд и проксирует `/api` на бэкенд.

## Ключевые решения

### Сборки подбирает алгоритм, а не LLM

Языковая модель может предложить несовместимые детали, выдумать цену или выйти за бюджет,
и проверить это заранее нельзя. Поэтому подбор полностью алгоритмический
(`backend/app/recommender/`), а модель только разбирает запрос и пересказывает готовый результат:

- перебираются все пары «процессор + видеокарта» (каталог небольшой, поэтому полный перебор
  быстрый и даёт точный результат, а не приблизительный);
- каждая пара достраивается до полной сборки по долям бюджета, которые зависят от сценария
  (в играх больше денег уходит на видеокарту, в работе — на процессор и память);
- каждую сборку проверяют правила совместимости: сокеты, тип и количество памяти, слоты M.2,
  длина видеокарты и высота кулера в корпусе, мощность блока питания, баланс CPU и GPU;
- оставшиеся деньги тратятся на улучшения с лучшим приростом оценки на рубль. Улучшение
  с маленьким приростом не принимается, даже если деньги остались.

Результат воспроизводим и покрыт тестами: каждое правило совместимости проверяется на случае
с нарушением и без, а подбор — на свойствах вроде «сборка дороже — оценка не ниже».

### ИИ необязателен, ошибка модели не ломает приложение

Каждый сценарий с LLM имеет вариант без неё (`backend/app/ai/service.py`):

| Сценарий | С LLM | Без LLM или при ошибке |
|---|---|---|
| Разбор запроса «игровой ПК за 120к» | модель возвращает JSON, его проверяет Pydantic | разбор правилами (регулярные выражения) |
| Объяснение сборки | текст модели потоком | объяснение по шаблону из тех же фактов |

В ответе API есть поле `source` (`llm`, `rules`, `template`), поэтому интерфейс знает, кто
сформировал текст. Провайдеры скрыты за общим интерфейсом: Anthropic Claude или любой
OpenAI-совместимый API, включая локальные модели в LM Studio. Локальные серверы поддерживают
разные способы вернуть JSON, поэтому провайдер пробует их по очереди (`json_object` →
`json_schema` → инструкция в промпте) и запоминает рабочий. Таймауты без повторов:
локальная модель на слабой видеокарте не должна считать один ответ дважды.

### Потоковое объяснение с отменой генерации

Объяснение приходит по мере генерации в формате NDJSON (`POST /api/ai/explain/stream`):

- данные о сборке считаются до начала потока, поэтому ошибка подбора приходит обычным
  кодом 422, а не обрывом посреди ответа;
- если модель сбилась на середине, сервер сообщает об этом последним событием, и фронтенд
  убирает оборванный текст и показывает объяснение по шаблону;
- когда пользователь уходит со страницы или выбирает другую сборку, фронтенд отменяет запрос,
  а бэкенд закрывает соединение с LLM. Иначе модель дописывала бы ненужный ответ, а следующее
  объяснение ждало бы её;
- в Docker nginx проксирует `/api` без буферизации, иначе текст пришёл бы одним куском в конце.

### Как уменьшить выдумки модели

Маленькие локальные модели часто «додумывают»: пишут о предупреждениях, которых нет, или выдают
остаток бюджета за экономию. Что помогло:

- данные для модели — короткие готовые фразы с русскими ключами вместо машинных кодов
  (английские ключи модель вставляла прямо в текст);
- пустые поля явно заполнены словом «нет»: без поля «предупреждения» модель придумывала их сама;
- низкая температура генерации;
- скрипт `backend/scripts/eval_explanations.py` прогоняет типовые сборки через модель и
  автоматически ищет выдуманные предупреждения, числа, которых нет в данных, неверный тип памяти
  и т. п. Его стоит запускать после каждой правки промпта или смены модели.

### Вход — сессии в базе, а не JWT

После входа браузер получает случайный токен в httpOnly-cookie, а в таблице `user_sessions`
хранится только его SHA-256. Почему не JWT:

- выход и «выйти на всех устройствах» должны срабатывать сразу. JWT действует до истечения
  срока, и отозвать его можно только через то же хранилище на сервере, то есть
  преимущество «без состояния» теряется;
- бэкенд один, и запрос к таблице сессий по уникальному индексу ничего не стоит;
- фронтенд и API открываются с одного адреса (nginx, в разработке — прокси Vite), поэтому
  cookie работает без настройки CORS, а скрипты на странице токен не видят.

Остальное:

- пароли хешируются argon2id. Если адреса нет в базе, проверка всё равно идёт по фиктивному
  хешу: по времени ответа нельзя узнать, зарегистрирован ли адрес, а текст ошибки одинаковый;
- от CSRF защищает `SameSite=Lax`: с чужого сайта браузер не отправит cookie в POST-запросе;
- попытки входа и регистрации ограничены `AUTH_RATE_LIMIT_PER_MINUTE` с одного адреса;
- сохранять сборки можно и без входа. Сборки вошедшего пользователя попадают в «Мои сборки»,
  удалить сборку может только её владелец.

### Redis — общее состояние воркеров, каталог — в памяти процесса

Бэкенд работает в несколько процессов (воркеры uvicorn, `WEB_CONCURRENCY`), и у каждого
своя память. Через Redis они делят то, что должно быть общим:

- **Лимиты запросов.** Скользящее окно в отсортированном множестве Redis: элемент — запрос,
  score — его время. Lua-скрипт атомарно удаляет старые записи, считает оставшиеся и добавляет
  новую, поэтому два воркера не могут одновременно занять последнее место. Время берётся
  у Redis, а не у воркеров: часы разных машин могут расходиться. С лимитами в памяти каждый
  воркер считал бы сам, и лимит умножался бы на число воркеров.
- **Версия каталога.** Сам каталог Redis не хранит: каждый процесс держит его в памяти
  готовыми объектами, и подбору не нужны ни запрос к базе, ни разбор JSON. Redis хранит
  только номер версии (`catalog:version`). Импорт цен и сид увеличивают его после commit,
  а воркер перед запросом сверяет номер (один `GET`) и при расхождении перечитывает каталог.
  На всякий случай каталог перечитывается и раз в `CATALOG_CACHE_SECONDS` (5 минут).
- **Готовые результаты подбора** (`app/response_cache.py`, заголовок ответа `X-Cache: HIT/MISS`).
  Ключ — параметры запроса и отпечаток каталога (id и цены всех деталей): после импорта цен
  ключи меняются сами, и устаревший результат вернуть нельзя. Зачем это нужно, показал
  нагрузочный тест (см. «Нагрузочное тестирование»).

Загрузка каталога из PostgreSQL занимает около 16 мс, проверка кэша — микросекунды:
`GET /api/components` ускорился с 25 до 10 мс. На подборе это почти незаметно:
там время уходит на перебор сборок, а не на базу.

Redis необязателен, и его отказ не роняет API:

- без `REDIS_URL` лимиты считаются в памяти процесса, каталог обновляется по TTL;
- при ошибке Redis то же самое включается автоматически. После первой ошибки срабатывает
  предохранитель (`redis_client.Breaker`): запросы перестают обращаться к Redis, а фоновый
  поток раз в 5 секунд проверяет, ожил ли он, и сам включает его обратно. Без предохранителя
  каждый запрос ждал бы таймаута, а если контейнер Redis остановлен — ещё и DNS
  (в Docker это около 8 секунд). Так это ожидание достаётся только первому запросу после
  отказа. Проверено вручную: `docker stop pcbuilder-redis` — API продолжает отвечать
  за миллисекунды, после `docker start` Redis подхватывается сам;
- `/api/health/ready` сообщает состояние Redis (`ok`, `error`, `disabled`), но 503 отдаёт
  только при недоступной базе: без Redis экземпляр продолжает обслуживать запросы.

### Типы фронтенда генерируются из OpenAPI

FastAPI строит OpenAPI-схему по Pydantic-моделям, а фронтенд получает из неё
TypeScript-типы (`openapi-typescript`), вместо того чтобы повторять их вручную:

```bash
uv run python backend/scripts/export_openapi.py   # схема -> frontend/openapi.json
cd frontend && npm run gen:api                     # типы  -> frontend/src/api-schema.ts
```

Оба файла лежат в репозитории, поэтому изменение API видно в diff pull request.
В `src/types.ts` у сгенерированных типов короткие имена (`Component`, `Recommendation`...),
а тела запросов в `src/api.ts` проверяются через `satisfies` по схемам `*In`.
CI выгружает схему заново и падает, если она или типы разошлись с закоммиченными:
поменять ответ API и забыть про фронтенд не получится, а TypeScript покажет каждое
место, где фронтенд использует изменившееся поле.

Чтобы типы были точными, схемы бэкенда описывают допустимые значения: перечисления
и `Literal` вместо `str` (`tier`, `level`, `kind`, `source`). Во фронтенде они становятся
union-типами вроде `'upgrade' | 'saving'`. Вручную описано только событие потока
объяснения: NDJSON-поток в OpenAPI не описывается.

### Логика не зависит от базы и HTTP

Совместимость и подбор работают с обычными объектами в памяти, сборка неизменяема
(замена детали возвращает новую сборку, что удобно при переборе вариантов). Поэтому почти все
тесты идут без PostgreSQL. Подробнее — в разделе «Архитектура».

## Запуск для разработки

Нужны: Python 3.14 и [uv](https://docs.astral.sh/uv/), Docker с Docker Compose, Node.js 20+.

```bash
# 1. Настройки окружения
cp .env.example .env

# 2. База данных и Redis (порты на хосте 5433 и 6380). Redis необязателен:
#    чтобы бэкенд им пользовался, укажите в .env REDIS_URL=redis://localhost:6380/0
docker compose up -d db redis

# 3. Зависимости бэкенда
uv sync

# 4. Миграции и тестовые данные
cd backend
uv run alembic upgrade head
uv run python -m app.seed

# 5. Бэкенд: http://localhost:8000, документация API: http://localhost:8000/docs
uv run uvicorn app.main:app --reload

# 6. Фронтенд (в отдельном терминале, из корня проекта): http://localhost:5173
cd frontend
npm install
npm run dev
```

Vite проксирует запросы `/api/*` на бэкенд, поэтому отдельно настраивать адрес API не нужно.

### Подключение ИИ (необязательно)

В `.env` укажите провайдера и ключ:

```ini
# Anthropic (модель по умолчанию — claude-opus-5-5)
LLM_PROVIDER=anthropic
LLM_API_KEY=sk-ant-...

# или любой OpenAI-совместимый API
LLM_PROVIDER=openai
LLM_API_KEY=...
LLM_MODEL=имя-модели
LLM_BASE_URL=https://адрес-api/v1   # для OpenAI можно не указывать
```

После изменения `.env` перезапустите бэкенд. Статус виден в правом верхнем углу интерфейса.

Если бэкенд запущен в Docker, а модель — на этом же компьютере (LM Studio, Ollama),
в `LLM_BASE_URL` вместо `localhost` укажите `host.docker.internal`, например
`http://host.docker.internal:1234/v1`.

### Обновление цен

Цены обновляются из прайс-листа поставщика в CSV с колонками `brand`, `name` и `price_rub`
(пример — `prices/prices.example.csv`). Разделитель — запятая или точка с запятой,
цену можно записать как `12 990` или `12990,00`. Детали ищутся по бренду и названию:
их id меняются при повторном заполнении базы.

```bash
cd backend
uv run python -m app.prices ../prices/prices.csv --dry-run   # только отчёт
uv run python -m app.prices ../prices/prices.csv             # записать цены

# В Docker: импорт ./prices/prices.csv раз в час (интервал — PRICES_IMPORT_INTERVAL)
docker compose --profile prices up -d
```

Если цена изменилась больше чем на 50%, она не применяется и попадает в отчёт:
такое изменение чаще означает ошибку в выгрузке (лишний ноль), чем реальное подорожание.
Порог задаёт `--max-change`. Строки, которые не удалось разобрать, и детали, которых нет
в каталоге, тоже попадают в отчёт. Бэкенд перезапускать не нужно: после импорта
увеличивается версия каталога в Redis, и бэкенд перечитывает каталог со следующего запроса
(без Redis — в течение `CATALOG_CACHE_SECONDS`).

## Тесты и проверки

```bash
uv run pytest                     # тесты
uv run ruff check backend         # линтер
uv run ruff format backend        # форматирование (в CI — ruff format --check)
cd backend && uv run mypy         # проверка типов
cd frontend && npm run lint && npm test && npm run build
cd frontend && npm run gen:api    # типы API после выгрузки схемы (см. «Типы фронтенда»)
cd frontend && npm run test:e2e   # e2e на Playwright (один раз: npx playwright install chromium)
```

Те же проверки запускает GitHub Actions на каждый push и pull request
(`.github/workflows/ci.yml`). В CI тесты идут с настоящим PostgreSQL, типы API сверяются
со схемой бэкенда, а в конце
собирается и запускается весь стек в Docker и проверяется подбор через nginx.

Тесты не требуют запущенной базы: модули совместимости и подбора работают с объектами
в памяти, а API-тесты подменяют загрузку каталога данными из JSON. Тесты, которым нужен
PostgreSQL (загрузка каталога, сохранённые сборки), пропускаются, если база не запущена.
Каждый из них идёт в транзакции, которая в конце откатывается, поэтому данные в базе
не меняются. ИИ тестируется с фейковым провайдером, реальных запросов к модели нет.

| Файл | Что проверяет |
|---|---|
| `test_catalog.py` | полнота и согласованность тестовых данных, загрузка из БД |
| `test_compatibility.py` | каждое правило совместимости: случай с нарушением и без |
| `test_recommender.py` | распределение бюджета, модель оценки, свойства подбора, предпочтения, замены, объяснения |
| `test_api.py` | эндпоинты, валидация, ошибки, применение замены |
| `test_ai.py` | разбор запроса правилами и через LLM, запасные варианты при ошибках LLM |
| `test_eval_explanations.py` | проверки скрипта оценки объяснений |

### Оценка точности объяснений

Модульные тесты не проверяют, что пишет настоящая модель. Для этого есть скрипт: он
генерирует объяснения для нескольких типовых сборок через провайдер из `.env` и ищет
типичные ошибки — выдуманные предупреждения и экономию, «дороже бюджета» для сборки
в бюджете, числа, которых нет в данных, служебные слова из JSON, не тот тип памяти.

```bash
uv run python backend/scripts/eval_explanations.py --runs 3 --out eval.json
uv run python backend/scripts/eval_explanations.py --rescore eval.json   # перепроверить без генерации
```

База и бэкенд не нужны. Скрипт стоит запускать после правок промпта или смены модели.
Проверки ловят не всё (например, неверную оценку доплаты), поэтому сохранённые тексты
полезно просмотреть.

## Схема БД

### Пользователи

```
users          (id PK, email UNIQUE, password_hash, created_at)
user_sessions  (id PK, user_id FK → users ON DELETE CASCADE, token_hash UNIQUE, created_at, expires_at)
```

- `email` хранится в нижнем регистре, поэтому уникальность не зависит от регистра.
- `token_hash` — SHA-256 токена из cookie. Сам токен в базе не хранится: даже при утечке
  таблицы войти под чужой сессией нельзя. Истёкшие сессии пользователя удаляются при его входе.

### Сохранённые сборки

```
saved_builds       (id PK, slug UNIQUE, params JSONB, tier, created_at,
                    user_id FK → users ON DELETE SET NULL)
saved_build_parts  (build_id FK → saved_builds ON DELETE CASCADE, position,
                    component_id FK → components ON DELETE RESTRICT, price_rub)
```

- `slug` — 8 случайных символов (`secrets.token_urlsafe`), а не id: по ссылке нельзя
  перебрать чужие сборки. Уникальность проверяет база; при совпадении код создаётся заново.
- `params` — параметры подбора: при открытии ссылки сборка оценивается и получает
  объяснение и замены так же, как на странице подбора.
- `price_rub` в `saved_build_parts` — цена детали на момент сохранения. Сборка показывается
  по текущим ценам, а по сохранённым видно, насколько она подорожала или подешевела.
- Ключ детали — `(build_id, position)`, а не `(build_id, component_id)`: в сборке может
  быть два одинаковых накопителя, и порядок деталей сохраняется.
- `RESTRICT` не даёт удалить из каталога деталь, на которую ссылается сохранённая сборка.
- `user_id` пустой у сборок, сохранённых без входа. `SET NULL` при удалении пользователя
  сохраняет ссылки, которыми он уже поделился.

### Каталог комплектующих

Используется наследование таблиц (joined table inheritance). Общие поля всех
комплектующих хранятся в `components`, характеристики категории — в отдельной
таблице, связанной с `components` по `id` (1:1). SQLAlchemy по полю `category`
понимает, объект какого класса создать.

```
components (id PK, category, brand, name, price_rub, perf_score, power_w, price_updated_at)
   ├── cpus          (id PK/FK → components.id, ...)
   ├── gpus          (id PK/FK, ...)
   ├── motherboards  (id PK/FK, ...)
   ├── rams          (id PK/FK, ...)
   ├── storages      (id PK/FK, ...)
   ├── psus          (id PK/FK, ...)
   ├── cases         (id PK/FK, ...)
   └── coolers       (id PK/FK, ...)
```

| Таблица | Поля |
|---|---|
| `components` | id, category, brand, name, price_rub, perf_score (0–100), power_w, price_updated_at |
| `cpus` | socket, cores, threads, base_ghz, boost_ghz, memory_types[], has_igpu, includes_cooler, multicore_score |
| `gpus` | chip, vram_gb, length_mm, recommended_psu_w |
| `motherboards` | socket, chipset, form_factor, memory_type, memory_slots, max_memory_gb, m2_slots |
| `rams` | memory_type, capacity_gb, modules, speed_mhz |
| `storages` | kind (NVMe / SATA_SSD / HDD), interface (M.2 / SATA), capacity_gb |
| `psus` | wattage, efficiency |
| `cases` | supported_form_factors[], max_gpu_length_mm, max_cooler_height_mm, max_radiator_mm |
| `coolers` | kind (air / aio), height_mm, radiator_mm, sockets[], max_tdp_w |

`perf_score` — оценка производительности внутри категории (0–100). У процессоров это
игровая производительность (100 = Ryzen 7 9800X3D), многопоточная (рендер, видео)
хранится отдельно в `cpus.multicore_score`. У видеокарт 100 = RTX 5090. Оценки
приблизительно отражают соотношения из общедоступных тестов.

Тестовые данные: `backend/app/seed/components.json`. В нём 138 позиций (15–23 на
категорию), платформы AMD AM4/AM5 и Intel LGA1700/LGA1851, цены от бюджетного
до топового сегмента. Цены примерные и служат только для демонстрации.

## Модуль совместимости

`backend/app/compatibility/`. Сборка проверяется набором независимых правил.
Каждое правило — функция `(сборка) -> список нарушений`. Нарушение содержит:
- уровень: `error` — собрать нельзя, `warning` — собрать можно, но есть риск;
- машинный код;
- понятный текст;
- id затронутых деталей.

Правило проверяет только уже выбранные детали, поэтому модуль работает и с неполной сборкой.

| Правило | Уровень | Что проверяет |
|---|---|---|
| `cpu_motherboard_socket` | error | сокет процессора и платы |
| `cooler_socket` | error | кулер поддерживает сокет |
| `cooler_tdp` | warning | кулер справляется с тепловыделением CPU |
| `board_vrm` | warning | мощный процессор (от 150 Вт) на плате начального уровня (A520, A620, H610) |
| `ram_type` | error | тип памяти: RAM ↔ плата ↔ процессор |
| `ram_slots_and_capacity` | error | число модулей ≤ слотов, объём ≤ максимума платы |
| `m2_slots` | error | хватает слотов M.2 |
| `board_form_factor` | error | форм-фактор платы поддерживается корпусом |
| `gpu_length` | error | видеокарта помещается в корпус |
| `cooler_fits_case` | error | высота кулера / размер радиатора СЖО |
| `psu_power` | error / warning | мощность БП ≥ потребления; запас ≥ 30% и не ниже рекомендации производителя GPU |
| `cpu_gpu_balance` | warning | процессор не ограничивает видеокарту и не избыточен для неё (с учётом разрешения) |

Для законченной сборки (`complete=True`) дополнительно проверяется, что выбраны
все обязательные детали, есть вывод изображения (видеокарта или встроенная графика)
и охлаждение (отдельный кулер или боксовый).

- **Потребление сборки** — сумма `power_w` всех деталей.
- **Рекомендуемый БП** — потребление × 1,3, округлённое вверх до 50 Вт, но не ниже
  рекомендации производителя видеокарты.
- **Баланс CPU/GPU** (`app/balance.py`). Шкалы оценок CPU и GPU разные, поэтому процессор
  считается достаточным, если `cpu_score ≥ gpu_score × K` (допуск 3%). K зависит от
  разрешения: 1,2 для 1080p, 1,0 для 1440p, 0,7 для 4K. Чем выше разрешение, тем больше
  нагрузка ложится на видеокарту. Процессор избыточен, если `cpu_score > gpu_score × 2,7`.
- **Ручной режим** использует `candidate_errors(сборка, деталь)`: деталь показывается,
  если её установка не порождает ошибок, в которых участвует она сама. Несовместимые детали
  можно показать вместе с причиной.

## Алгоритм рекомендаций

`backend/app/recommender/`. Вход — `RecommendRequest`:
- бюджет;
- сценарий (`gaming`, `workstation`, `office`);
- разрешение (для игр);
- необязательно: платформа (AMD/Intel), конкретный процессор или видеокарта.

### 1. Распределение бюджета (`budget.py`)

Для каждого сценария задана таблица долей:

| | CPU | GPU | Плата | RAM | SSD | БП | Корпус | Охлаждение |
|---|---|---|---|---|---|---|---|---|
| Игры | 20% | 40% | 10% | 8% | 7% | 7% | 5% | 3% |
| Видео и 3D | 30% | 28% | 10% | 12% | 8% | 6% | 4% | 2% |
| Офис и учёба | 35% | 0% | 15% | 12% | 15% | 10% | 10% | 3% |

В играх доля видеокарты зависит от разрешения: −4% в 1080p, +6% в 4K. Эти проценты
забираются у процессора (60%) и платы (40%).

Доли — ориентир для второстепенных деталей: в каждой категории берётся лучшая деталь,
которая укладывается в свою долю. Процессор и видеокарта перебираются полностью
(шаг 3), поэтому их доли используются для сравнения «план / факт» на диаграмме.

### 2. Оценка сборки (`scoring.py`)

Оценка 0–100 — взвешенная сумма оценок по «ролям»:

```
score = Σ вес(сценарий, роль) × оценка(роль)
```

| Роль | Игры | Видео и 3D | Офис |
|---|---|---|---|
| игровая производительность связки CPU+GPU | 0,80 | — | — |
| процессор | 0,05 (игровая) | 0,34 (многопоточная) | 0,50 (среднее) |
| видеокарта | — | 0,34 | — |
| память | 0,07 | 0,16 | 0,20 |
| накопитель | 0,05 | 0,11 | 0,25 |
| платформа (плата, БП, корпус, охлаждение) | 0,03 | 0,05 | 0,05 |

Ключевые идеи модели:

- **Число кадров определяет более слабое звено.**
  `gaming = min(gpu_score, cpu_score / K(разрешение))`. Деньги, вложенные в видеокарту
  сверх возможностей процессора (или наоборот), оценку не повышают. Поэтому алгоритм
  сам выбирает сбалансированные пары.
- **Убывающая отдача.** Объём памяти и накопителя сверх полезного для сценария не повышает
  оценку. Для памяти это 32 ГБ в играх, 128 ГБ в работе, 16 ГБ в офисе; для накопителя —
  2, 4 и 1 ТБ. Все NVMe считаются одинаково быстрыми: разница между бюджетным и топовым
  в играх и офисе почти незаметна.
- **Двухканальная память.** Один модуль памяти штрафуется, а при встроенной графике сильнее:
  она использует ОЗУ как видеопамять.
- **Видеокарты для 3D.** В сценарии «Видео и 3D» видеокарты не NVIDIA учитываются
  с коэффициентом 0,8: в Blender и DaVinci Resolve NVIDIA быстрее за счёт CUDA/OptiX.

### 3. Поиск сборок (`builder.py`)

Для каждого варианта задан предел цены: «Дешевле» — 80% бюджета, «Оптимальная» — 100%,
«С запасом» — 115%.

1. **Перебор пар.** Перебираются все пары (процессор, видеокарта) с учётом предпочтений.
   Для офиса видеокарта не ставится, а процессор нужен со встроенной графикой.
   Каталог небольшой (~23 × 19 пар), поэтому полный перебор занимает доли секунды
   и даёт точный результат.
2. **Достройка.** Каждая пара достраивается до полной сборки: плата → память →
   накопитель → кулер → корпус → блок питания. Для каждой детали берутся только
   совместимые варианты, отвечающие требованиям сценария. Из них выбирается деталь
   с наибольшим вкладом в оценку в пределах своей доли бюджета, при равенстве — более
   дешёвая. Если в долю не укладывается ничего, берётся самая дешёвая.
3. **Требования сценария.** Сборки ниже этого уровня не рассматриваются:
   - минимум памяти: в играх 16 ГБ, при бюджете от 90 тыс. — 32 ГБ;
   - системный диск — только SSD;
   - видеопамяти не меньше 8 ГБ;
   - блок питания только с сертификатом 80 PLUS;
   - нет предупреждений о слабом кулере, нехватке запаса БП и слабом питании платы.
4. **Докупка улучшений.** Лучшие 12 сборок «докупаются»: оставшиеся деньги жадно тратятся
   на замену второстепенной детали с лучшим приростом оценки на рубль. Улучшение
   принимается, только если оно даёт не меньше 30% от средней «оценки за рубль» всей
   сборки, иначе деньги не тратятся. Так система не тратит бюджет на то,
   что почти не влияет на результат.
5. **Выбор.** Берётся сборка с наибольшей оценкой, а если несколько сборок отличаются
   меньше чем на 1% — самая дешёвая. У варианта «С запасом» к оценке добавляется бонус
   за возможность апгрейда:
   - +3 за актуальный сокет AM5/LGA1851;
   - +2 за блок питания с запасом 50%;
   - +1 за свободные слоты памяти.
6. **Отсев похожих.** Победители более дешёвых вариантов участвуют в выборе более дорогих,
   поэтому более дорогой вариант никогда не хуже. Вариант показывается, только если он
   хотя бы на 2% лучше предыдущего. Поэтому иногда вариантов два, а не три.

Если даже самая дешёвая подходящая сборка дороже бюджета, пользователь получает
понятное сообщение с минимальной суммой.

### 4. Замены (`alternatives.py`)

Для каждой детали перебираются все детали той же категории. Если замена ломает
совместимость (например, процессор другого сокета), зависимые детали подбираются
заново самые дешёвые (`BuildSearch.repair`), и все вынужденные изменения показываются
пользователю. Для каждой замены считаются разница в цене и изменение оценки в процентах.

- **«Что даст доплата»:** прирост ≥ 2%, доплата ≤ 30% бюджета, лучшие по приросту на рубль.
  Доплата с низкой отдачей помечается «мало пользы за эти деньги».
- **«Где сэкономить»:** экономия ≥ 1000 ₽ при потере не больше 3%.
- Закреплённые пользователем процессор и видеокарта не заменяются.

Любую замену можно применить одним нажатием: сборка пересчитывается через
`POST /api/recommend/evaluate`, и для неё строятся новые замены.

### 5. Объяснение (`explain.py`)

Из сборки собираются «факты»:
- распределение денег;
- что ограничивает FPS;
- запас блока питания;
- платформа;
- предупреждения;
- лучшие замены.

По фактам строится шаблонное объяснение. Если подключён ИИ, те же факты в JSON
передаются модели с инструкцией пересказать их простым языком, ничего не добавляя от себя.

### Производительность

Замер: `uv run python backend/scripts/bench_recommend.py` (медиана 9 прогонов, база не нужна;
с флагом `--profile` показывает профиль cProfile).

| Запрос | До | После |
|---|---|---|
| игры 1080p, 70 тыс. | 625 мс | 335 мс |
| игры 1440p, 120 тыс. | 811 мс | 538 мс |
| игры 4K, 250 тыс. | 1031 мс | 768 мс |
| работа, 180 тыс. | 1011 мс | 767 мс |
| офис, 45 тыс. | 124 мс | 95 мс |
| **в среднем** | **721 мс** | **501 мс (−30%)** |

Что сделано по профилю:
- **Кэш оценки и проверки сборки** внутри одного подбора. Одни и те же сборки оцениваются
  много раз: в каждом из трёх вариантов, при докупке улучшений и при поиске замен.
  Ключ — набор id деталей (`Build.key`).
- **Сборка неизменяема** (`frozen=True`), поэтому ключ, цена и потребление считаются
  один раз (`cached_property`), а не при каждом обращении. Копирование сборки — прямым
  вызовом конструктора вместо `dataclasses.replace`.
- **Самая дешёвая деталь** выбирается без расчёта пользы для всех вариантов: польза
  считается только среди деталей с минимальной ценой.

Результаты подбора не изменились: до и после правок сравнивались 120 запросов (все бюджеты,
сценарии, разрешения и платформы) — состав, оценки, замены и объяснения совпадают.

Что не делалось и почему:
- **Отказ от ORM-объектов в подборе.** По профилю около 20% времени уходит на чтение полей
  ORM-объектов: у SQLAlchemy каждое обращение к полю проходит через дескриптор. Убрать это
  можно, только переведя подбор на простые классы вместо ORM-моделей, — крупная переделка
  ради такого выигрыша.

### Нагрузочное тестирование

Сценарии k6 — `loadtest/k6.js`, запросы идут через nginx, как у браузера:

```bash
docker compose up -d --build
docker compose --profile loadtest run --rm --no-deps k6 run -e SCENARIO=mixed -e RATE=20 /scripts/k6.js
loadtest/bench.sh   # вся таблица ниже: каждый сценарий на 2 и 8 воркерах, с кэшем и без (~18 минут)
```

| Сценарий | Что делает |
|---|---|
| `catalog` | ручная сборка: каталог, варианты деталей, проверка совместимости |
| `recommend` | только подбор; бюджет — как с ползунка (40–300 тыс. с шагом 5000), 477 разных запросов |
| `mixed` | смесь, похожая на живых пользователей: 60% ручная сборка, 20% открыть сохранённую сборку, 20% подбор; постоянная частота `RATE` сценариев в секунду |

Замеры: 60 секунд на точку. Весь стек и k6 работают на одной машине (Docker Desktop
на Windows, 8 vCPU), поэтому цифры — для сравнения вариантов, а не обещание для продакшена.
Ошибок нет ни в одном замере.

**Что нашёл тест.**

1. **Подбор упирается в CPU.** Один подбор — около 0,6 с процессорного времени, и вся машина
   держит лишь 2,5 подбора в секунду на 2 воркерах и 4,5 на 8. Хуже другое: пока воркер
   считает подбор, остальные запросы этого воркера ждут (GIL), и у лёгких запросов, которые
   отвечают за 3 мс, p95 вырастает до сотен миллисекунд.
2. **У nginx кончались порты.** К бэкенду открывалось новое TCP-соединение на каждый
   запрос, закрытые соединения ещё минуту занимают порт (TIME_WAIT), и при ~700 RPS
   за минуту порты заканчивались: 17–34% запросов получали 502 «Address not available».
   В коротких прогонах по 20 секунд этого видно не было. Исправлено постоянными
   соединениями (`keepalive` в `frontend/nginx/default.conf`).

**Что сделано.** Кэш результатов подбора в Redis (см. «Redis — общее состояние воркеров»)
и keepalive в nginx. Число воркеров задаётся `WEB_CONCURRENCY`, по умолчанию 2; на сервере
его стоит ставить по числу ядер.

Лёгкие запросы (`catalog`, 50 одновременных пользователей):

| Воркеров | Без keepalive | С keepalive |
|---|---|---|
| 2 | 560 RPS, 17% ошибок | 685 RPS, p95 128 мс, без ошибок |
| 8 | 697 RPS, 34% ошибок | 1172 RPS, p95 104 мс, без ошибок |

Смесь (`mixed`), медиана / p95. Кэш прогревается по ходу прогонов: доля попаданий указана
для каждого замера.

| Воркеров, сценариев/с | Кэш | RPS | Лёгкие запросы | Подбор | Попадания |
|---|---|---|---|---|---|
| 2, 20 | нет | 23 (не успевает, 350 сценариев отброшено) | 5–11 с / 16–20 с | 13 с / 21 с | — |
| 2, 20 | да | 42 | 150–220 мс / 2 с | 0,45 с / 6,3 с | 61% |
| 8, 20 | нет | 41 | 60–80 мс / 450–500 мс | 2,4 с / 11 с | — |
| 8, 20 | да | 44 | 3 мс / 110–190 мс | 22 мс / 2,3 с | 72% |
| 8, 40 | да | 88 | 3 мс / 50–65 мс | 3 мс / 0,84 с | 90% |

Итого: на 2 воркерах без кэша стек перегружен уже при 20 сценариях в секунду (очередь
растёт, ответы по 10–20 секунд), а с кэшем и 8 воркерами держит 40 сценариев в секунду
(~88 RPS) с p95 лёгких запросов около 60 мс. Подбор при промахе кэша по-прежнему стоит
около 0,6 с CPU, поэтому p95 подбора — это промахи. Следующий шаг, если понадобится:
выносить подбор в отдельный пул процессов, чтобы он не задерживал лёгкие запросы того же
воркера, или ускорять сам алгоритм (см. «Что не делалось» выше).

## Слой ИИ

`backend/app/ai/`. Провайдер заменяемый: интерфейс `LLMProvider` (`base.py`) содержит
два метода — `generate_json` и `generate_text`. Реализации:

- `AnthropicProvider` — официальный SDK `anthropic`, структурированный вывод по JSON-схеме.
  Если классификатор безопасности модели ошибочно отклонит запрос, работает серверный
  запасной вариант (`fallbacks`).
- `OpenAICompatibleProvider` — SDK `openai` с настраиваемым `base_url`. Подходит для OpenAI,
  DeepSeek, локальной Ollama и других совместимых сервисов.

Чтобы добавить провайдера, нужно реализовать два метода и добавить его в `factory.py`.

| Задача | С LLM | Без LLM или при ошибке |
|---|---|---|
| Разбор запроса («хочу играть в 1440p до 120 тысяч») | модель извлекает бюджет, сценарий, разрешение, платформу, модели деталей; ответ проверяется Pydantic | разбор по ключевым словам и регулярным выражениям (`rules_parser.py`) |
| Объяснение сборки | модель пересказывает факты простым языком | шаблонное объяснение |

Названия деталей из запроса («RTX 5070») сопоставляются с каталогом, и такая деталь
закрепляется в подборе.

## Эксплуатация

- **Логи.** Каждая запись содержит request-id. Он берётся из заголовка `X-Request-ID`
  (в Docker его ставит nginx) или создаётся заново и возвращается клиенту в том же
  заголовке, поэтому ошибку из интерфейса легко найти в логах. О каждом запросе пишется
  метод, путь, код ответа и время. `LOG_JSON=true` включает JSON-формат, одна запись на строку,
  для сборщиков логов; в Docker он включён.
- **Ограничение запросов к ИИ.** Не больше `AI_RATE_LIMIT_PER_MINUTE` (по умолчанию 20)
  запросов к `/api/ai/parse` и `/api/ai/explain*` в минуту с одного адреса, дальше —
  ответ 429 с заголовком `Retry-After`. С `REDIS_URL` счётчики общие для всех воркеров
  и экземпляров бэкенда, без него — в памяти процесса.
- **Проверки здоровья.** Docker Compose считает бэкенд готовым по `/api/health/ready`,
  и nginx стартует только после этого.
- **Cookie сессии.** За HTTPS включите `COOKIE_SECURE=true`, чтобы браузер не отправлял
  cookie по незашифрованному соединению. Срок жизни сессии — `SESSION_TTL_DAYS` (30 дней).
- **CORS** задаётся переменной `CORS_ORIGINS`. Нужен, только когда фронтенд открыт с другого
  адреса, как Vite в разработке; в Docker фронтенд и API на одном адресе.
- **База.** Подключение ограничено 5 секундами (`connect_timeout`): если база недоступна,
  запрос быстро получает ошибку, а не висит.

### Метрики и мониторинг

```bash
docker compose --profile monitoring up -d
# Grafana: http://localhost:3000 — дашборд «Конфигуратор ПК» открывается сразу, без входа
# Prometheus: http://localhost:9090, активные алерты — http://localhost:9090/alerts
```

Бэкенд отдаёт метрики в формате Prometheus на `/metrics` (`app/metrics.py`). Путь вне `/api`,
поэтому nginx его наружу не отдаёт: метрики видит только Prometheus внутри сети Compose.

| Метрика | Что показывает |
|---|---|
| `http_requests_total{method, route, status}` | запросы к API |
| `http_request_duration_seconds{method, route}` | время ответа (гистограмма) |
| `http_requests_in_progress` | запросы в работе: растёт, когда воркеры не успевают |
| `recommend_cache_total{result}`, `recommend_compute_seconds` | попадания в кэш подбора и время самого подбора |
| `rate_limited_total{limiter}` | отказы по лимитам (429): ИИ и вход |
| `ai_responses_total{kind, source}` | кто ответил: модель (`llm`) или запасной вариант (`rules`, `template`) |
| `redis_breaker_trips_total`, `catalog_reloads_total` | отключения Redis предохранителем, загрузки каталога |

Решения:

- **Метка — шаблон маршрута** (`/api/builds/{slug}`), а не путь: иначе каждая ссылка на сборку
  стала бы отдельным временным рядом. Запросы мимо маршрутов (сканеры, опечатки) попадают
  в одну метку `unmatched`.
- **Несколько воркеров.** У каждого процесса свои счётчики, и без общего хранилища Prometheus
  видел бы только тот воркер, которому достался его запрос. Поэтому включён multiprocess-режим
  `prometheus_client`: воркеры пишут значения в файлы `PROMETHEUS_MULTIPROC_DIR`, `/metrics`
  суммирует их. Папка очищается при старте контейнера. Проверено: k6 отправил 1310 запросов,
  Prometheus насчитал столько же.
- **Дашборд и источник данных — в репозитории** (`monitoring/grafana`), Grafana загружает их
  при старте. Правила алертов — `monitoring/prometheus/alerts.yml`: бэкенд недоступен, больше
  5% ошибок 5xx, p95 лёгких запросов больше 0,5 с, Redis отключался. Отправка алертов
  (Alertmanager) не настроена.
- **CI** проверяет конфиг и правила (`promtool`), поднимает мониторинг и убеждается, что
  Prometheus видит бэкенд, а Grafana загрузила дашборд.

Метрики сразу нашли проблему. Под нагрузкой предохранитель Redis срабатывал с «Timeout
reading from socket», хотя Redis работал: пока воркер считает подбор, поток с запросом
к Redis может не получать GIL дольше 0,5 с, и ответ считался опоздавшим. Предохранитель
на 5 секунд выключал кэш, подборы считались заново, и нагрузка росла ещё больше.
Таймаут чтения увеличен до 2 с (таймаут подключения остался 0,5 с, недоступный Redis
по-прежнему обнаруживается быстро). После этого при полной загрузке CPU — ни одного
срабатывания.

## Цены

Цены хранятся в базе. Модуль `app/prices/provider.py` содержит интерфейс
`PriceProvider.fetch_prices(components) -> list[PriceQuote]`, заглушку
`StaticPriceProvider` и функцию `update_prices(session, provider)`, которая
записывает новые цены в базу. Чтобы подключить парсер магазина, достаточно
написать класс с методом `fetch_prices`.
